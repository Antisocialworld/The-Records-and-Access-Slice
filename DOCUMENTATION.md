# The Records and Access Slice — Documentation

## 1. What This Is

This slice implements signed-in users creating, listing, viewing, and deleting their own Project records. The record type is deliberately generic — a Project has only a `title` and a `createdAt` timestamp. The core substance of the slice is ownership enforcement, access control at the query level, and data-access efficiency measured by actual query counts. Every endpoint and page enforces that a user can only see and manipulate their own records; a request for another user's project returns `404`, never `403`, to prevent resource enumeration.

Authentication is passwordless email OTP with an optional Everyday Code (short PIN for quick sign-in). The schema has no `password` column — the original bcrypt password flow was replaced by explicit directive override. Users are auto-provisioned on first successful OTP verification. The sign-in flow is: enter email → receive 6-digit OTP (logged to console in dev mode) → enter code → session created. Users with an Everyday Code set can alternatively sign in with a 4-8 digit PIN. The Everyday Code is bcrypt-hashed on the `User` row and locks out after 5 failed attempts; signing in via OTP resets the lockout.

## 2. How To Run It

```bash
# 1. Environment — set AUTH_SECRET (pepper for session tokens) and DATABASE_URL
echo 'AUTH_SECRET="replace-with-a-real-secret"' > .env
echo 'DATABASE_URL="file:./dev.db"' >> .env
echo 'PRISMA_QUERY_LOGGING="false"' >> .env

# 2. Database migration
npx prisma migrate dev

# 3. Seed — creates Alice (alice@example.test) and Bob (bob@example.test)
#    with one session each; prints their dev tokens to stdout
node --env-file=.env prisma/seed.js

# 4. Start the dev server
npm run dev
```

The root page (`/`) redirects to `/projects` if authenticated, or `/signin` if not. The sign-in page is a multi-step client component: email entry → method selection (if Everyday Code is set) → code verification (OTP 6-digit input or Everyday Code PIN).

## 3. The Flow, Step By Step

1. **Authentication — sign-in flow** — The sign-in page (`src/app/signin/page.tsx`) is a multi-step client component. Step 1: email entry → `POST /api/auth/check-email` (validates format, returns `exists` + `hasEverydayCode`). Step 2: if the user has an Everyday Code, a method selection screen offers "Send fresh email OTP" or "Use my Everyday Code"; if no Everyday Code, OTP is auto-triggered. Step 3a (OTP): `POST /api/auth/request-otp` generates a 6-digit numeric code, hashes it with bcrypt, stores it in `OtpCode` with a 10-minute TTL, and logs the plaintext to the dev server console. The user enters the code in 6 segmented input boxes. `POST /api/auth/verify-otp` finds the latest unconsumed, unexpired `OtpCode`, verifies the hash, increments `attempts` on failure (burns the code at 3 attempts), and on success upserts the `User` (auto-provisioning on first sign-in), creates a `Session`, and sets the `session` cookie. Step 3b (Everyday Code): `POST /api/auth/verify-everyday-code` checks the user's `everydayCodeHash` with bcrypt, enforces a 5-attempt lockout (`everydayCodeFailedAttempts`), and on success creates a session. `POST /api/auth/logout` destroys the session and clears the cookie.

2. **Scoped project listing** — `GET /api/projects` (defined in `src/app/api/projects/route.ts`) calls `listProjectsForUser(userId)` in `src/lib/projects.ts`. The Prisma query is `findMany({ where: { userId }, orderBy: { createdAt: "desc" }, select: { publicId, title, createdAt } })`. The `userId` lives inside the `where` clause — there is no "fetch all then filter" step. The compound index `@@index([userId, createdAt])` covers both the filter and the sort.

3. **Project creation** — `POST /api/projects` validates the `title` (required, ≤ 200 chars), then calls `createProjectForUser(userId, title)`. The `publicId` is generated by `newPublicId()` which calls `crypto.randomBytes(16).toString("base64url")` — 22 URL-safe characters, cryptographically random, non-sequential, leaking nothing about the database primary key. The response returns `{ project: { publicId, title, createdAt } }` with status `201`.

4. **Scoped detail view** — The URL `/projects?project=<publicId>` triggers the server component at `src/app/projects/page.tsx`, which calls `getProjectForUser(userId, publicId)`. The Prisma query is `findUnique({ where: { userId_publicId: { userId, publicId } } })`. The compound unique constraint `@@unique([userId, publicId])` means the query hits the index directly. If the project doesn't exist or belongs to another user, `null` is returned and the user is redirected to `/projects`.

5. **Atomic deletion and audit trail** — `DELETE /api/projects/[publicId]` calls `deleteProjectForUser(userId, publicId)` in `src/lib/projects.ts`. This function first runs a scoped existence check (`findUnique` scoped by `userId`), then executes `prisma.$transaction([auditLog.create(...), project.delete(...)])`. The audit row — recording `userId`, `action: "DELETE_PROJECT"`, and `targetPublicId` — is written **before** the delete. If the project doesn't exist, no audit row is created and `false` is returned, triggering a `404`. The `targetPublicId` is a plain `String`, not a foreign key, so deleting the project does not cascade away the audit evidence.

6. **Everyday Code management** — Authenticated users can set, update, or remove their Everyday Code from `/settings/security`. `POST /api/user/everyday-code` validates the code is 4-8 digits, bcrypt-hashes it, stores it on the `User` row, and resets `everydayCodeFailedAttempts`. `DELETE /api/user/everyday-code` sets the hash to null. The security settings page (`src/app/settings/security/page.tsx`) is a server component that checks auth, queries the user's Everyday Code status, and renders a client component for the form.

## 4. The Data Model

### User

| Column | Type | Notes |
|---|---|---|
| `id` | `String` (cuid) | Primary key |
| `email` | `String` | Unique |
| `createdAt` | `DateTime` | Default `now()` |
| `everydayCodeHash` | `String?` | Null = not configured |
| `everydayCodeUpdatedAt` | `DateTime?` | Last Everyday Code change |
| `everydayCodeFailedAttempts` | `Int` | Default 0; lockout counter |

No `password` column. Auth was overridden from bcrypt to passwordless.

### Session

| Column | Type | Notes |
|---|---|---|
| `id` | `String` (cuid) | Primary key |
| `userId` | `String` | FK → User (cascade delete) |
| `token` | `String` | Unique; stores `sha256(AUTH_SECRET + ":" + raw_token)` |
| `expiresAt` | `DateTime` | 7-day TTL |
| `createdAt` | `DateTime` | Default `now()` |

Indexes: `@@index([userId])`, `@@index([token])`.

### OtpCode

| Column | Type | Notes |
|---|---|---|
| `id` | `String` (cuid) | Primary key |
| `email` | `String` | Not unique — keyed by email, not userId |
| `codeHash` | `String` | bcrypt hash of the OTP |
| `expiresAt` | `DateTime` | Code expiry |
| `attempts` | `Int` | Default 0 |
| `consumedAt` | `DateTime?` | Null until used |
| `createdAt` | `DateTime` | Default `now()` |

Index: `@@index([email, createdAt])`. Used by the passwordless OTP flow — rate-limit queries count recent pending codes per email.

### Project

| Column | Type | Notes |
|---|---|---|
| `id` | `String` (cuid) | Primary key — never exposed to clients |
| `publicId` | `String` | `crypto.randomBytes(16).toString("base64url")` |
| `userId` | `String` | FK → User (cascade delete) |
| `title` | `String` | Max 200 chars enforced at API level |
| `createdAt` | `DateTime` | Default `now()` |

Constraints:
- `@@index([userId, createdAt])` — covers the scoped list query and its `ORDER BY createdAt DESC` sort in a single index scan.
- `@@unique([userId, publicId])` — enforces that a `publicId` is unique per user (not globally), and serves the scoped detail lookup directly.

### AuditLog

| Column | Type | Notes |
|---|---|---|
| `id` | `String` (cuid) | Primary key |
| `userId` | `String` | FK → User (cascade delete) |
| `action` | `String` | e.g. `"DELETE_PROJECT"` |
| `targetPublicId` | `String` | **Not** a foreign key — plain string snapshot |
| `createdAt` | `DateTime` | Default `now()` |

Indexes: `@@index([userId, createdAt])`, `@@index([action])`.

`targetPublicId` is deliberately **not** a foreign key relation to `Project`. A cascading FK would delete the audit trail when the project is deleted — the exact evidence the audit must preserve. A plain string keeps the trail intact.

## 5. The Concepts

### 1. Authentication vs Authorisation

**What it is:** Authentication proves who you are (session cookie → `User` row). Authorisation determines what you're allowed to do (owner-scoped queries).

**Why it's needed:** Without both, either anonymous users access data (missing auth) or authenticated users access each other's data (missing authorisation).

**How it's implemented:** `getSessionUser()` in `src/lib/auth.ts` handles authentication — it reads the cookie, hashes the token, looks up the session, and returns the user. Every function in `src/lib/projects.ts` takes `userId` as its first parameter and embeds it in the Prisma `where` clause — this is the authorisation boundary. The route handlers in `src/app/api/projects/route.ts` and `src/app/api/projects/[publicId]/route.ts` call `getSessionUser()` first (auth), then pass `user.id` to the scoped data function (authz).

**What was chosen against:** A middleware-based auth layer was rejected because Next.js middleware runs on the edge and cannot access the database directly in all deployment targets. Placing the auth check inside each route handler keeps the security boundary explicit and testable per endpoint.

### 2. Query Scoping vs Post-Fetch Checking

**What it is:** Query scoping puts the ownership constraint inside the database query (`where: { userId }`). Post-fetch checking fetches the record first, then compares ownership in application code.

**Why it's needed:** Post-fetch checking is a classic source of IDOR bugs — if a developer forgets the ownership check after the fetch, another user's data leaks. Query scoping makes it structurally impossible to return a row that doesn't belong to the caller.

**How it's implemented:** Every function in `src/lib/projects.ts` — `listProjectsForUser`, `createProjectForUser`, `getProjectForUser`, `deleteProjectForUser` — takes `userId` and places it inside `where`. There is no "fetch by publicId then compare" variant.

**What was chosen against:** A `findUnique({ where: { publicId } })` followed by `if (project.userId !== user.id)` was rejected because it requires every future developer to remember the comparison. The scoped pattern makes forgetting impossible.

### 3. Insecure Direct Object References (IDOR)

**What it is:** IDOR occurs when an application uses user-supplied input (like a database ID) to access objects directly, without checking ownership.

**Why it's needed:** If `/api/projects/123` fetches project `123` without scoping by user, any authenticated user can enumerate IDs and access any project.

**How it's implemented:** The URL uses `publicId` (random, non-sequential), not the database `id`. Every query scopes by `userId`. A request for `/api/projects/<someone-elses-public-id>` returns `404` because the scoped query `where: { userId, publicId }` finds nothing.

**What was chosen against:** Exposing the auto-incrementing `id` was rejected from the start (PRD Requirement 2). Sequential IDs are trivially guessable.

### 4. Why Raw DB Identifiers Aren't Exposed (`publicId` pattern)

**What it is:** The `publicId` is a `crypto.randomBytes(16).toString("base64url")` — 22 URL-safe characters of cryptographic randomness. It is the only identifier visible in URLs and API responses.

**Why it's needed:** Database IDs reveal implementation details (table name, row count, insertion order). Random publicIds prevent enumeration, information leakage, and cache-poisoning attacks.

**How it's implemented:** `newPublicId()` in `src/lib/projects.ts` generates the ID. The `@@unique([userId, publicId])` constraint ensures uniqueness per user. All `select` clauses in `projects.ts` return `{ publicId, title, createdAt }` — the raw `id` is never selected.

**What was chosen against:** UUIDs (v4) were considered but `base64url` is shorter (22 chars vs 36) and URL-safe without encoding.

### 5. Audit Logging (Atomic `$transaction`)

**What it is:** An immutable record of who did what and when. For this slice, the only audited action is `DELETE_PROJECT`.

**Why it's needed:** Without an audit trail, a user could delete a project and there would be no evidence it ever existed. The audit log preserves the `targetPublicId` and `action` even after the record is gone.

**How it's implemented:** `deleteProjectForUser()` in `src/lib/projects.ts` runs `prisma.$transaction([auditLog.create(...), project.delete(...)])`. The audit row is written **first**. The `targetPublicId` is a plain `String` (not a FK), so deleting the project does not cascade away the audit.

**What was chosen against:** A separate `auditLog.create()` call outside the transaction was rejected because if the app crashes between audit and delete, the trail exists for a record that wasn't deleted — inconsistent state.

### 6. Page Architecture (Conditional Rendering + `searchParams` URL State)

**What it is:** The `/projects` page is a single server component that reads `searchParams` and conditionally renders one of four client components. Every view state is addressable via its URL.

**Why it's needed:** A single route avoids proliferating pages for what is conceptually one resource. Bookmarkable URLs mean users can share links to specific views. Server-side rendering with `searchParams` means the correct data is fetched on every navigation.

**How it's implemented:** `src/app/projects/page.tsx` is a server component with `export const dynamic = "force-dynamic"`. It reads `searchParams` (a `Promise` in Next 16), checks for `new=1`, `project=<id>`, and `delete=1`, then renders `<ProjectList>`, `<CreateProjectForm>`, `<ProjectDetail>`, or `<DeleteConfirm>`. All navigation uses `<Link>` or `router.push()` — no full page reloads.

| URL | View |
|---|---|
| `/projects` | Project list (or empty state) |
| `/projects?new=1` | Create project form |
| `/projects?project=<publicId>` | Project detail |
| `/projects?project=<publicId>&delete=1` | Confirm delete |

**What was chosen against:** Separate pages (`/projects/new`, `/projects/[publicId]`) were considered but the single-route approach matches the PRD's "conditional view rendering" requirement and keeps the URL structure flat.

### 7. 401 Unauthorized vs 403 Forbidden vs 404 Not Found (Existence Masking)

**What it is:** Three distinct HTTP status codes with precise semantic meaning.

**Why it's needed:** Mixing them leaks information. A `403` on someone else's project confirms the project exists. A `404` does not.

**How it's implemented:**

| Status | When | Where |
|---|---|---|
| `401` | No valid session cookie | `getSessionUser()` returns `null` → `unauthorized()` on pages, `401 JSON` on API routes |
| `403` | Authenticated but forbidden for non-ownership reasons | Currently unused; documented for completeness |
| `404` | Record not found OR owned by another user | `getProjectForUser()` returns `null` → `404 JSON` or redirect |

**What was chosen against:** Returning `403` for "not your project" was rejected because it confirms the resource exists to another user. `404` masks existence.

### 8. Database Indexing (Compound index `Project_userId_createdAt_idx`)

**What it is:** A compound B-tree index on `(userId, createdAt)` that covers both the filter and the sort in a single index scan.

**Why it's needed:** Without the index, SQLite performs a full table scan for every `WHERE userId = ?` query, then a filesort for `ORDER BY createdAt DESC`. With the compound index, the query planner can seek to the `userId` prefix and scan in `createdAt` order — no sort step.

**How it's implemented:** `@@index([userId, createdAt])` in `prisma/schema.prisma` on the `Project` model. The `@@unique([userId, publicId])` constraint also creates an index, but it serves a different query pattern (point lookup by `userId + publicId`).

**What was chosen against:** A separate `@@index([userId])` was considered redundant because the compound index already covers plain `userId` lookups (the leading column).

### 9. Query Count as Cost (`PRISMA_QUERY_LOGGING`, measurement & reduction)

**What it is:** Every Prisma query is a round-trip to the database. Minimising query count per request reduces latency and load.

**Why it's needed:** An unoptimised delete might run: (1) fetch by publicId, (2) check ownership, (3) create audit, (4) delete project = 4 queries. A transaction with a scoped existence check can do it in 3.

**How it's implemented:** Set `PRISMA_QUERY_LOGGING=true` in `.env` to enable `log: ["query"]` on the Prisma client (`src/lib/prisma.ts`). Each query is logged to stdout. The current `deleteProjectForUser` runs: (1) scoped `findUnique` (existence check), (2) `$transaction` containing `auditLog.create` + `project.delete` = 3 queries total.

**What was chosen against:** Fetching the full project record before delete was rejected because we only need the `id` for the delete — the `select: { id: true }` on the existence check is the minimal data needed.

### 10. SQLite vs PostgreSQL Tradeoffs for a Single-Tester Slice

**What it is:** SQLite is a file-based, serverless database. PostgreSQL is a client-server database with full ACID, concurrency, and extensions.

**Why it's needed:** The choice affects deployment simplicity, concurrency limits, and feature availability.

**How it's implemented:** SQLite via `file:./dev.db` in `prisma/schema.prisma`. Zero configuration, single-file database, instant setup. The `DATABASE_URL` in `.env` points to the file.

**What was chosen against:** PostgreSQL was considered for production-grade features (JSONB, full-text search, row-level locking). For a single-tester assessment slice, SQLite's simplicity wins. The concurrency limitation (single-writer lock) is acceptable at this scale.

## 6. What Went Wrong

### Access Control Audit Table

| `GET` | `/api/projects/<Alice's publicId>` | Alice's token | 200 | 200 | ✅ |
| `GET` | `/api/projects/<Alice's publicId>` | Bob's token | 404 | 404 | ✅ |
| `GET` | `/api/projects/<Bob's publicId>` | Bob's token | 200 | 200 | ✅ |
| `GET` | `/api/projects/<Bob's publicId>` | Alice's token | 404 | 404 | ✅ |

### Engineering Findings

- **Foreign key cascade on audit trails** — The original `AuditLog.targetId` was considered as a FK to `Project`. This was rejected because `onDelete: Cascade` would delete the audit row when the project is deleted — the exact evidence the audit must preserve. The column was renamed to `targetPublicId` and made a plain `String`.
- **AUTH_SECRET must be set** — `src/lib/session-token.js` falls back to an empty string if `AUTH_SECRET` is missing (`process.env.AUTH_SECRET ?? ""`). This means session tokens have no pepper and a database leak exposes raw tokens. The `.env.example` documents this but the agent cannot set the value — the user must.
- **Session token module as CommonJS** — `src/lib/session-token.js` is intentionally CommonJS (`require`/`module.exports`) so the plain-Node seed script (`prisma/seed.js`) can import it without a build step. The `allowJs: true` flag in `tsconfig.json` lets the Next app import it too.
- **PowerShell quote mangling** — Windows PowerShell 5.1 silently strips or corrupts nested quotes in `curl --data`. The workaround is writing JSON to a file and using `--data-binary "@body.json"`.
- **npm install latency** — Fresh `npm install` takes approximately 12 minutes in this environment. All dependencies were installed once and cached.
- **Single dev server lock** — Next.js 16 refuses to start a second `dev` server on the same port. The running server (PID 14652) must be killed before restarting.

## 7. What This Slice Does Not Handle

- **Editing** — Projects cannot be edited after creation. No `PUT` / `PATCH` endpoint exists.
- **Search** — No search or filtering beyond the scoped list.
- **Tags / categories** — No tagging or categorisation system.
- **Sharing / collaboration** — Projects are strictly single-owner. No sharing, invitations, or multi-user access.
- **Landing page or dashboard widgets** — The root page (`/`) redirects to `/projects`. There is no marketing page, onboarding flow, or dashboard.
- **Everyday Code** — `POST /api/user/everyday-code` (set/update, 4-8 digit PIN, bcrypt-hashed) and `DELETE /api/user/everyday-code` (remove). Accessible from `/settings/security` for authenticated users.
- **SQLite concurrency** — Under high parallel write load, SQLite acquires a single-writer lock. This is acceptable for a single-tester slice but would be a bottleneck in production.
- **CSRF protection** — API routes rely on `SameSite: Lax` cookies. No additional CSRF token mechanism is implemented.
- **Rate limiting** — No rate limiting on any endpoint.

## 8. If I Built This Again

The single most significant lesson is designing audit trail tables without hard foreign key deletion cascades from day one. The original schema had `AuditLog.targetId` as a plain string, but the temptation to add `@relation` and `onDelete: Cascade` is strong — and it would silently destroy audit evidence on project deletion. Making the "no FK" decision explicit in the schema comment and renaming the field to `targetPublicId` (rather than the ambiguous `targetId`) prevents future developers from assuming it's a relational column. If I were building this for production, I would add a dedicated `AuditEvent` table with a polymorphic `targetType` + `targetId` pair, a `metadata` JSON column for context, and a separate `Archive` table for soft-deleted records — all designed so that no cascade can ever remove the trail.
